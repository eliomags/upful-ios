Key Design Decisions:
- Single primary API Worker handles most routes (keeps wrangler.toml simple)
- Auth is a separate Worker for isolation and independent scaling
- Chat uses Durable Objects for stateful WebSocket connections
- D1 is the single source of truth for all structured data
- KV caches hot data (leaderboards, market quotes, sessions)
- R2 stores binary objects (avatars, chat images)
- Queues handle all async work (notifications, emails, payouts, ranking)
- Cron Triggers run on schedule for market data refresh and competition cycles


================================================================================
2. CLOUDFLARE WORKER ORGANIZATION
================================================================================

Workers are organized by domain responsibility. Each is independently
deployable but shares D1 bindings.

WORKER 1: api-main
-------------------
  Purpose: Primary REST API for all app features
  Routes:
    /api/v1/portfolio/*
    /api/v1/trade/*
    /api/v1/competition/*
    /api/v1/leaderboard/*
    /api/v1/notifications/*
    /api/v1/market/*
    /api/v1/admin/*
    /api/v1/user/profile*
    /api/v1/payments/*
  Bindings: D1 (primary), KV (cache, sessions), R2 (uploads), Queue (tasks)
  Size: Largest worker, organized internally with router pattern

WORKER 2: api-auth
-------------------
  Purpose: Authentication, registration, token management
  Routes:
    /api/v1/auth/*
  Bindings: D1 (primary), KV (sessions, rate-limit), R2 (none)
  Why separate: Auth logic is security-critical, benefits from isolation.
  Handles: Sign in with Apple, email/password, JWT issuance/refresh,
           SMS verification via Twilio, email verification via Resend

WORKER 3: api-chat
-------------------
  Purpose: Chat WebSocket upgrade and REST fallback
  Routes:
    /api/v1/chat/*
  Bindings: Durable Object (ChatRoom), D1 (message persistence),
            KV (user presence), R2 (image uploads)
  Why separate: WebSocket connections require Durable Objects which
  have different scaling characteristics.

WORKER 4: cron-worker
----------------------
  Purpose: Scheduled tasks (no external routes)
  Triggers:
    - Every 5 min:  Refresh market quotes for active tickers
    - Every 15 min: Recalculate leaderboard rankings
    - Every 1 hour: Clean expired KV cache entries
    - Daily 00:00 UTC: Roll daily competition, calculate daily winners
    - Monday 00:00 UTC: Roll weekly competition, calculate weekly winners
    - 1st of month 00:00 UTC: Roll monthly competition, monthly winners
    - Daily 06:00 UTC: Fetch market data bulk update (pre-market)
    - Daily 22:00 UTC: Snapshot portfolio values for all active users
  Bindings: D1 (primary), KV (cache), Queue (tasks)

Internal Router Pattern (for api-main):
  Uses itty-router or Hono framework for route matching.
  Middleware chain: CORS -> RateLimit -> Auth -> Handler -> ErrorHandler

wrangler.toml bindings (shared):
  [[d1_databases]]
  binding = "DB"
  database_name = "upful-primary"
  database_id = "<auto>"

  [[kv_namespaces]]
  binding = "CACHE"
  id = "<auto>"

  [[kv_namespaces]]
  binding = "SESSIONS"
  id = "<auto>"

  [[r2_buckets]]
  binding = "STORAGE"
  bucket_name = "upful-storage"

  [[queues.producers]]
  binding = "TASK_QUEUE"
  queue = "upful-tasks"

  [[queues.consumers]]
  queue = "upful-tasks"
  max_batch_size = 10
  max_batch_timeout = 30

3. D1 DATABASE SCHEMA (COMPLETE SQL)

-- ============================================================
-- USERS & AUTHENTICATION
-- ============================================================

CREATE TABLE users (
    id              TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    email           TEXT UNIQUE NOT NULL,
    username        TEXT UNIQUE NOT NULL,
    display_name    TEXT,
    password_hash   TEXT,                   -- NULL if Sign-in-with-Apple only
    apple_user_id   TEXT UNIQUE,            -- Sign in with Apple subject ID
    avatar_key      TEXT,                   -- R2 object key for avatar
    paypal_email    TEXT,                   -- For prize payouts
    phone           TEXT,                   -- For SMS verification
    phone_verified  INTEGER DEFAULT 0,      -- 0=no, 1=yes
    email_verified  INTEGER DEFAULT 0,      -- 0=no, 1=yes
    subscription_tier TEXT DEFAULT 'free',  -- 'free' | 'premium'
    subscription_expires_at TEXT,           -- ISO8601, NULL if free
    apple_original_transaction_id TEXT,     -- StoreKit 2 original txn ID
    role            TEXT DEFAULT 'user',    -- 'user' | 'admin' | 'moderator'
    is_banned       INTEGER DEFAULT 0,
    ban_reason      TEXT,
    created_at      TEXT DEFAULT (datetime('now')),
    updated_at      TEXT DEFAULT (datetime('now'))
);

CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_username ON users(username);
CREATE INDEX idx_users_apple_user_id ON users(apple_user_id);
CREATE INDEX idx_users_subscription_tier ON users(subscription_tier);

-- ============================================================
-- DEVICE TOKENS (for APNs push notifications)
-- ============================================================

CREATE TABLE device_tokens (
    id          TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    user_id     TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token       TEXT NOT NULL,
    platform    TEXT DEFAULT 'ios',         -- 'ios' only for now
    is_active   INTEGER DEFAULT 1,
    created_at  TEXT DEFAULT (datetime('now')),
    updated_at  TEXT DEFAULT (datetime('now')),
    UNIQUE(user_id, token)
);

CREATE INDEX idx_device_tokens_user ON device_tokens(user_id);

-- ============================================================
-- REFRESH TOKENS
-- ============================================================

CREATE TABLE refresh_tokens (
    id          TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    user_id     TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash  TEXT NOT NULL UNIQUE,       -- SHA-256 of the refresh token
    device_id   TEXT,                       -- Identifies the device
    expires_at  TEXT NOT NULL,
    created_at  TEXT DEFAULT (datetime('now'))
);

CREATE INDEX idx_refresh_tokens_user ON refresh_tokens(user_id);
CREATE INDEX idx_refresh_tokens_hash ON refresh_tokens(token_hash);

-- ============================================================
-- PORTFOLIOS
-- ============================================================

CREATE TABLE portfolios (
    id              TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    user_id         TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    cash_balance    REAL NOT NULL DEFAULT 25000.00,
    total_equity    REAL NOT NULL DEFAULT 25000.00,
    is_active       INTEGER DEFAULT 1,      -- Only 1 active portfolio per user
    competition_month TEXT,                  -- '2026-02' format, ties portfolio to competition period
    created_at      TEXT DEFAULT (datetime('now')),
    updated_at      TEXT DEFAULT (datetime('now'))
);

CREATE INDEX idx_portfolios_user ON portfolios(user_id);
CREATE INDEX idx_portfolios_active ON portfolios(user_id, is_active);
CREATE INDEX idx_portfolios_month ON portfolios(competition_month);

-- ============================================================
-- POSITIONS (current holdings, derived from trades)
-- ============================================================

CREATE TABLE positions (
    id              TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    portfolio_id    TEXT NOT NULL REFERENCES portfolios(id) ON DELETE CASCADE,
    user_id         TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    ticker          TEXT NOT NULL,
    asset_type      TEXT NOT NULL DEFAULT 'stock',  -- 'stock'|'crypto'|'etf'|'bond'|'option'|'future'|'forex'
    quantity        REAL NOT NULL DEFAULT 0,         -- REAL to support fractional/forex
    average_cost    REAL NOT NULL DEFAULT 0,
    current_price   REAL DEFAULT 0,
    market_value    REAL DEFAULT 0,                  -- quantity * current_price
    unrealized_pnl  REAL DEFAULT 0,
    updated_at      TEXT DEFAULT (datetime('now')),
    UNIQUE(portfolio_id, ticker)
);

CREATE INDEX idx_positions_portfolio ON positions(portfolio_id);
CREATE INDEX idx_positions_user ON positions(user_id);
CREATE INDEX idx_positions_ticker ON positions(ticker);

-- ============================================================
-- TRADES (immutable transaction log)
-- ============================================================

CREATE TABLE trades (
    id              TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    portfolio_id    TEXT NOT NULL REFERENCES portfolios(id) ON DELETE CASCADE,
    user_id         TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    ticker          TEXT NOT NULL,
    asset_type      TEXT NOT NULL DEFAULT 'stock',
    side            TEXT NOT NULL,           -- 'buy' | 'sell'
    quantity        REAL NOT NULL,
    price           REAL NOT NULL,           -- Execution price
    total_value     REAL NOT NULL,           -- quantity * price
    order_type      TEXT DEFAULT 'market',   -- 'market' | 'limit' (future)
    status          TEXT DEFAULT 'filled',   -- 'filled' | 'cancelled'
    executed_at     TEXT DEFAULT (datetime('now')),
    created_at      TEXT DEFAULT (datetime('now'))
);

CREATE INDEX idx_trades_portfolio ON trades(portfolio_id);
CREATE INDEX idx_trades_user ON trades(user_id);
CREATE INDEX idx_trades_ticker ON trades(ticker);
CREATE INDEX idx_trades_executed ON trades(executed_at);

-- ============================================================
-- PORTFOLIO SNAPSHOTS (daily performance tracking)
-- ============================================================

CREATE TABLE portfolio_snapshots (
    id              TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    portfolio_id    TEXT NOT NULL REFERENCES portfolios(id) ON DELETE CASCADE,
    user_id         TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    snapshot_date   TEXT NOT NULL,            -- 'YYYY-MM-DD'
    cash_balance    REAL NOT NULL,
    holdings_value  REAL NOT NULL,
    total_equity    REAL NOT NULL,
    daily_pnl       REAL DEFAULT 0,          -- Change from previous day
    daily_pnl_pct   REAL DEFAULT 0,
    total_pnl       REAL DEFAULT 0,          -- Change from starting 25K
    total_pnl_pct   REAL DEFAULT 0,
    created_at      TEXT DEFAULT (datetime('now')),
    UNIQUE(portfolio_id, snapshot_date)
);

CREATE INDEX idx_snapshots_user_date ON portfolio_snapshots(user_id, snapshot_date);
CREATE INDEX idx_snapshots_date ON portfolio_snapshots(snapshot_date);
CREATE INDEX idx_snapshots_portfolio ON portfolio_snapshots(portfolio_id);

-- ============================================================
-- COMPETITIONS
-- ============================================================

CREATE TABLE competitions (
    id              TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    type            TEXT NOT NULL,            -- 'daily' | 'weekly' | 'monthly'
    status          TEXT DEFAULT 'active',    -- 'active' | 'calculating' | 'completed' | 'paid_out'
    start_date      TEXT NOT NULL,            -- ISO8601
    end_date        TEXT NOT NULL,            -- ISO8601
    total_prize_pool REAL DEFAULT 0,
    participant_count INTEGER DEFAULT 0,
    created_at      TEXT DEFAULT (datetime('now'))
);

CREATE INDEX idx_competitions_type_status ON competitions(type, status);
CREATE INDEX idx_competitions_dates ON competitions(start_date, end_date);

-- ============================================================
-- COMPETITION ENTRIES (one per user per competition)
-- ============================================================

CREATE TABLE competition_entries (
    id              TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    competition_id  TEXT NOT NULL REFERENCES competitions(id) ON DELETE CASCADE,
    user_id         TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    portfolio_id    TEXT NOT NULL REFERENCES portfolios(id),
    starting_equity REAL NOT NULL DEFAULT 25000.00,
    ending_equity   REAL,
    growth_pct      REAL DEFAULT 0,          -- ((ending - starting) / starting) * 100
    rank            INTEGER,                 -- Final rank (NULL until competition ends)
    prize_amount    REAL DEFAULT 0,
    prize_status    TEXT DEFAULT 'none',      -- 'none' | 'pending' | 'approved' | 'paid' | 'failed'
    created_at      TEXT DEFAULT (datetime('now')),
    updated_at      TEXT DEFAULT (datetime('now')),
    UNIQUE(competition_id, user_id)
);

CREATE INDEX idx_comp_entries_competition ON competition_entries(competition_id);
CREATE INDEX idx_comp_entries_user ON competition_entries(user_id);
CREATE INDEX idx_comp_entries_rank ON competition_entries(competition_id, rank);
CREATE INDEX idx_comp_entries_growth ON competition_entries(competition_id, growth_pct DESC);

-- ============================================================
-- LEADERBOARD CACHE (materialized view, rebuilt every 15 min)
-- ============================================================

CREATE TABLE leaderboard_cache (
    id              TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
    competition_id  TEXT NOT NULL REFERENCES competitions(id) ON DELETE CASCADE,

    rank            INTEGER NOT NULL,

    UNIQUE(competition_id, user_id)
);

CREATE INDEX idx_leaderboard_comp_rank ON leaderboard_cache(competition_id, rank);
CREATE INDEX idx_leaderboard_comp_tier ON leaderboard_cache(competition_id, subscription_tier, rank);

================================================================================
4. API ENDPOINT DEFINITIONS
================================================================================

Base URL: https://api.jyanik.com/api/v1
All responses: JSON with envelope { "ok": true, "data": {...} }
                                or { "ok": false, "error": {...} }
All timestamps: ISO8601 UTC
Auth: Bearer JWT in Authorization header (except public endpoints)

------------------------------------------------------------
4.1 AUTHENTICATION (api-auth worker)
------------------------------------------------------------

POST   /auth/register
  Body: { email, username, password }
  Response: { user, access_token, refresh_token }
  Notes: Sends verification email via Resend. Password hashed with bcrypt.

POST   /auth/login
  Body: { email, password }
  Response: { user, access_token, refresh_token }

POST   /auth/apple
  Body: { identity_token, authorization_code, full_name? }
  Response: { user, access_token, refresh_token }
  Notes: Validates Apple identity token. Creates user if first sign-in.

POST   /auth/refresh
  Body: { refresh_token }
  Response: { access_token, refresh_token }
  Notes: Rotates refresh token on each use.

POST   /auth/logout
  Auth: Required
  Body: { refresh_token }
  Notes: Invalidates refresh token, removes from D1.

POST   /auth/verify-email
  Body: { token }
  Notes: Token from email verification link.

POST   /auth/forgot-password
  Body: { email }
  Notes: Sends password reset email via Resend.

POST   /auth/reset-password
  Body: { token, new_password }

POST   /auth/send-sms-code
  Auth: Required
  Body: { phone }
  Notes: Sends 6-digit code via Twilio.

POST   /auth/verify-sms
  Auth: Required
  Body: { phone, code }

DELETE /auth/account
  Auth: Required
  Notes: Soft-deletes user account. Data retained 30 days per legal requirements.

------------------------------------------------------------
4.2 USER PROFILE
------------------------------------------------------------

GET    /user/profile
  Auth: Required
  Response: Full user profile including subscription status.

PUT    /user/profile
  Auth: Required
  Body: { display_name?, paypal_email?, username? }

POST   /user/avatar
  Auth: Required
  Body: multipart/form-data with image file
  Notes: Uploads to R2. Resizes to 256x256 on worker. Returns avatar URL.

DELETE /user/avatar
  Auth: Required
  Notes: Removes avatar from R2.

GET    /user/preferences
  Auth: Required
  Response: { preferences: [{ category, value }] }

PUT    /user/preferences

================================================================================
5. AUTHENTICATION FLOW
================================================================================

Two auth methods supported. Both produce the same JWT token pair.

------------------------------------------------------------
5.1 SIGN IN WITH APPLE
------------------------------------------------------------

  iOS App                    api-auth Worker             Apple Servers
  --------                   ---------------             -------------
    |                             |                           |
    |  ASAuthorizationController  |                           |
    |  (native prompt)           |                           |
    |                             |                           |
    |--- POST /auth/apple ------->|                           |
    |    { identity_token,        |                           |
    |      authorization_code,    |                           |
    |      full_name }            |                           |
    |                             |--- Fetch Apple JWKS ----->|
    |                             |<-- Public keys -----------|
    |                             |                           |
    |                             |  Verify identity_token:   |
    |                             |  - Decode JWT             |
    |                             |  - Verify signature       |
    |                             |  - Check iss, aud, exp    |
    |                             |  - Extract subject (sub)  |
    |                             |                           |
    |                             |  Lookup user by apple_user_id
    |                             |  If not found: create new user
    |                             |    (generate username from full_name
    |                             |     or "user_" + random suffix)
    |                             |                           |
    |                             |  Generate JWT pair:       |
    |                             |  - access_token (15 min)  |
    |                             |  - refresh_token (30 days)|
    |                             |  Store refresh_token_hash |
    |                             |  in D1 refresh_tokens     |
    |                             |                           |
    |<-- { user, tokens } --------|                           |

  Apple JWKS are cached in KV for 24 hours.

------------------------------------------------------------
5.2 EMAIL + PASSWORD
------------------------------------------------------------

  Registration:
    1. POST /auth/register { email, username, password }
    2. Worker hashes password with bcrypt (via wasm bcrypt lib)
    3. Insert user into D1 with email_verified=0
    4. Queue email verification via Resend
    5. Return user + tokens (limited access until verified)
    6. User taps link in email -> POST /auth/verify-email

  Login:
    1. POST /auth/login { email, password }
    2. Lookup user by email
    3. Compare bcrypt hash
    4. If match: generate JWT pair, return tokens
    5. If fail: 401 with "Invalid credentials" (no info leakage)

------------------------------------------------------------
5.3 JWT TOKEN STRUCTURE
------------------------------------------------------------

  Access Token (short-lived, 15 minutes):
    Header: { alg: "HS256", typ: "JWT" }
    Payload: {
      sub: "<user_id>",
      email: "user@example.com",
      username: "johndoe",
      tier: "premium",       -- "free" | "premium"
      role: "user",          -- "user" | "admin" | "moderator"
      iat: 1708000000,
      exp: 1708000900        -- 15 min
    }
    Signed with: HMAC-SHA256 using JWT_SECRET env var

  Refresh Token (long-lived, 30 days):
    Opaque random string (64 bytes, hex-encoded).
    SHA-256 hash stored in D1 refresh_tokens table.
    Rotated on each use (old token invalidated, new one issued).

------------------------------------------------------------
5.4 AUTH MIDDLEWARE
------------------------------------------------------------

  Every authenticated request goes through:
    1. Extract Bearer token from Authorization header
    2. Verify JWT signature and expiration
    3. Extract user claims from payload
    4. Attach user to request context (env.user)
    5. If token expired: return 401 with code "TOKEN_EXPIRED"
       (iOS app catches this, calls /auth/refresh, retries original request)

  Premium-only middleware (additional):
    1. Check env.user.tier === 'premium'
    2. If not: return 403 with code "PREMIUM_REQUIRED"


================================================================================
6. KV NAMESPACE STRATEGY
================================================================================

Two KV namespaces are used. KV is eventually consistent but extremely fast
for reads, making it ideal for caching and session data.

------------------------------------------------------------
NAMESPACE: SESSIONS
------------------------------------------------------------

Purpose: Refresh token validation, rate limiting counters, SMS codes

Key Pattern                          Value                    TTL
-----------                          -----                    ---
session:<token_hash>                 { user_id, device_id }   30 days
rate:<ip>:<endpoint>                 <count>                  1 minute
sms:<phone>:<code>                   { code, attempts }       10 minutes
email_verify:<token>                 { user_id }              24 hours
password_reset:<token>               { user_id }              1 hour
apple_jwks                           { keys: [...] }          24 hours

------------------------------------------------------------
NAMESPACE: CACHE
------------------------------------------------------------

Purpose: Market data, leaderboard, user data caching

Key Pattern                          Value                    TTL
-----------                          -----                    ---
quote:<ticker>                       { price, change, ... }   5 minutes
quotes:batch:<hash>                  [{ ticker, price, ... }] 5 minutes
chart:<ticker>:<range>               [{ date, ohlcv }]        varies*
company:<ticker>                     { name, desc, ... }      24 hours
news:general                         [{ title, url, ... }]    15 minutes
news:<ticker>                        [{ title, url, ... }]    15 minutes
search:<query>                       [{ ticker, name }]       1 hour
screener:<param_hash>                [{ ticker, ... }]        15 minutes
leaderboard:<comp_id>:<tier>:<page>  [{ rank, user, ... }]    5 minutes
user:position:<user_id>:<type>       { rank, growth_pct }     5 minutes
portfolio:summary:<user_id>          { equity, cash, ... }    2 minutes

* Chart TTLs by range:
  1D  -> 5 minutes
  5D  -> 15 minutes
  1M  -> 1 hour
  3M  -> 6 hours
  6M+ -> 24 hours

Cache invalidation strategy:
  - TTL-based expiration (primary mechanism)
  - Write-through for user-specific data (update cache on write)
  - Stale-while-revalidate pattern for market data
    (return cached data immediately, refresh async via queue)

8. DURABLE OBJECTS DESIGN
================================================================================

Durable Objects provide single-threaded, stateful execution. Used for chat
because WebSocket connections need persistent server-side state.

------------------------------------------------------------
8.1 ChatRoom Durable Object
------------------------------------------------------------

One global ChatRoom instance handles all connected users. If scaling
requires it, this can be sharded by ticker/topic in the future.

class ChatRoom {
  state: DurableObjectState
  sessions: Map<WebSocket, { user_id, username, tier }>
  lastBroadcast: number

  // HTTP handler (for REST fallback)
  async fetch(request) {
    if (request.headers.get("Upgrade") === "websocket") {
      return this.handleWebSocket(request)
    }
    return this.handleHTTP(request)
  }

  // WebSocket lifecycle
  async handleWebSocket(request) {
    // 1. Validate auth token from query params
    // 2. Check premium status
    // 3. Accept WebSocket upgrade
    // 4. Add to sessions map
    // 5. Send recent messages (last 50) as initial payload
    // 6. Broadcast presence update
  }

  // Incoming message handler
  async webSocketMessage(ws, message) {
    // 1. Parse JSON message
    // 2. Validate content (length, content policy)
    // 3. Extract ticker mentions ($AAPL, $TSLA)
    // 4. Handle image if present (upload to R2)
    // 5. Persist to D1 via fetch to api-main
    // 6. Broadcast to all connected sessions
  }

  // Disconnection
  async webSocketClose(ws) {
    // 1. Remove from sessions
    // 2. Broadcast updated presence count
  }

  // Periodic cleanup (alarm)
  async alarm() {
    // Clean up stale sessions (no heartbeat in 5 min)
  }
}

Scaling considerations:
  - Single DO can handle ~100-200 concurrent WebSockets comfortably
  - If >500 users online simultaneously, shard by first letter of username
    or create "rooms" (General, Stocks, Crypto, etc.)
  - Each DO runs in a single Cloudflare location, close to the first
    requester. Global users may experience ~100ms latency, acceptable for chat.

------------------------------------------------------------
8.2 DO vs Alternative Approaches
------------------------------------------------------------

Why Durable Objects for chat (not polling or KV):
  - Real-time delivery: WebSocket push is instant vs. polling delay
  - Connection state: Track who is online
  - Ordered broadcast: Single-threaded guarantees message ordering
  - Cost: DO is cheaper than polling KV every second for N users

Why NOT Durable Objects for leaderboard:
  - Leaderboard is read-heavy, write-infrequent (every 15 min)
  - KV cache with cron rebuild is simpler and cheaper
  - No real-time requirement (5-minute staleness is acceptable)

9. QUEUE DESIGN FOR ASYNC TASKS
================================================================================

Single Cloudflare Queue: upful-tasks
Consumer: cron-worker (or dedicated queue-consumer worker)

Message format: { type: string, payload: object, priority?: number }

------------------------------------------------------------
9.1 TASK TYPES
------------------------------------------------------------

NOTIFICATION TASKS
  { type: "send_push", payload: { user_id, title, body, data } }
    -> Fetch device token from D1
    -> Send via APNs (HTTP/2 to api.push.apple.com)
    -> APNs auth via JWT signed with Apple P8 key

  { type: "send_push_batch", payload: { user_ids: [], title, body, data } }
    -> Batch push for competition events (start, end)

  { type: "send_email", payload: { to, subject, template, variables } }
    -> Send via Resend API
    -> Templates: welcome, verify_email, reset_password,
       prize_won, monthly_summary

  { type: "send_sms", payload: { phone, message } }
    -> Send via Twilio API
    -> Used only for phone verification

COMPETITION TASKS
  { type: "calculate_rankings", payload: { competition_id } }
    -> Fetch all entries for competition
    -> Calculate growth_pct for each
    -> Sort and assign ranks
    -> Update leaderboard_cache table
    -> Invalidate KV leaderboard cache

  { type: "roll_competition", payload: { type: 'daily'|'weekly'|'monthly' } }
    -> End current competition of this type
    -> Calculate final rankings and prizes
    -> Create new competition
    -> Auto-enroll active users
    -> Queue prize notifications

  { type: "assign_prizes", payload: { competition_id } }
    -> Apply prize structure based on competition type
    -> Create payout records with status 'pending'
    -> Queue notifications to winners

  { type: "snapshot_portfolios" }
    -> For each active user: calculate total equity
    -> Insert portfolio_snapshot record
    -> Used by daily cron at 22:00 UTC

PAYOUT TASKS
  { type: "process_payout", payload: { payout_id } }
    -> Fetch payout record
    -> If PayPal: send via PayPal Payouts API
    -> If Stripe: create Stripe Transfer
    -> Update payout status
    -> Queue notification to user

MARKET DATA TASKS
  { type: "refresh_quotes", payload: { tickers: [] } }
    -> Fetch from free financial APIs
    -> Update market_quotes in D1
    -> Update KV cache

  { type: "refresh_positions", payload: { user_id } }
    -> Fetch latest prices for user's positions
    -> Update positions table
    -> Recalculate portfolio equity

CLEANUP TASKS
  { type: "cleanup_chat", payload: {} }
    -> Delete chat messages older than 3 months
    -> Delete associated R2 images

  { type: "cleanup_sessions", payload: {} }
    -> Delete expired refresh tokens from D1

------------------------------------------------------------
9.2 QUEUE CONFIGURATION
------------------------------------------------------------

  max_batch_size: 10       -- Process up to 10 messages at a time
  max_batch_timeout: 30    -- Wait up to 30s to fill a batch
  max_retries: 3           -- Retry failed messages up to 3 times
  dead_letter_queue: upful-tasks-dlq  -- Dead letter for inspection

  Consumer concurrency: handled by Cloudflare (auto-scales)

  Error handling in consumer:
    - Each message processed in try/catch
    - On failure: log error, message auto-retried by queue
    - After max_retries: message goes to DLQ
    - DLQ monitored via Cloudflare dashboard

Strategy: Aggregate from multiple free APIs, cache aggressively, serve
from cache. The app does not need real-time data -- delayed quotes

------------------------------------------------------------

SOURCE 2: Alpha Vantage (free tier)

  Good for: Company fundamentals, financial statements

SOURCE 3: Finnhub (free tier)

  Good for: Search, company profiles, news

SOURCE 4: Twelve Data (free tier)
  Base: https://api.twelvedata.com
  Key: Free (800 credits/day, 8 per minute)
  Data: Time series, quote, crypto
  Good for: Chart data, crypto prices

SOURCE 5: CoinGecko (free tier)
  Base: https://api.coingecko.com/api/v3
  Data: Crypto prices, market data
  Rate limit: 10-50 calls/minute
  Good for: All crypto data

SOURCE 6: Exchange Rates API / Frankfurter
  Base: https://api.frankfurter.app
  Data: Forex rates
  Rate limit: Generous
  Good for: Forex trading pairs

------------------------------------------------------------
10.2 DATA AGGREGATION STRATEGY
------------------------------------------------------------

  Priority waterfall per data type:

  STOCK QUOTES:
    1. Yahoo Finance (primary, fastest)
    2. Finnhub (fallback)
    3. Alpha Vantage (last resort, strict rate limits)

  HISTORICAL CHARTS:
    1. Yahoo Finance (best OHLCV data)
    2. Twelve Data (good time series)
    3. Alpha Vantage (daily only on free tier)

  COMPANY INFO:
    1. Finnhub (company profile)
    2. Alpha Vantage (company overview)
    3. Yahoo Finance (summary detail)

  MARKET NEWS:
    1. Finnhub (market news endpoint)
    2. Yahoo Finance (news feed)

  CRYPTO:
    1. CoinGecko (comprehensive crypto data)
    2. Twelve Data (crypto time series)

  FOREX:
    1. Frankfurter (ECB rates)
    2. Twelve Data (forex pairs)

  STOCK SEARCH:
    1. Finnhub (symbol lookup)
    2. Yahoo Finance (search/autosuggest)

------------------------------------------------------------
10.3 CACHING LAYERS
------------------------------------------------------------

  Layer 1: KV Cache (fast reads, TTL-based)
    quote:<ticker> -> 5 min TTL
    chart:<ticker>:<range> -> 5 min to 24 hr depending on range

  Layer 2: D1 market_quotes table (persistent cache)
    Updated by cron every 5 minutes for tracked tickers
    "Tracked tickers" = union of all user positions + watchlists

  Layer 3: D1 market_history table (permanent storage)
    Historical OHLCV data, never expires
    Backfilled on first request, then updated daily by cron

  Read flow for GET /market/quote/AAPL:
    1. Check KV cache -> if hit and fresh, return
    2. Check D1 market_quotes -> if updated within 5 min, return + update KV
    3. Fetch from Yahoo Finance -> update D1 + KV -> return
    4. If Yahoo fails, try Finnhub -> same update flow
    5. If all fail, return stale D1 data with "stale: true" flag

------------------------------------------------------------
10.4 TRACKED TICKERS MANAGEMENT
------------------------------------------------------------

  The cron worker maintains a list of "active tickers" that need
  regular price updates. This set is the union of:

  SELECT DISTINCT ticker FROM positions
  UNION
  SELECT DISTINCT ticker FROM watchlist
  UNION
  SELECT DISTINCT ticker FROM (
    SELECT ticker FROM trades
    WHERE executed_at > datetime('now', '-7 days')
  )

  This query runs once per cron cycle. Result cached in KV as
  "active_tickers" with 1-hour TTL.

  Tickers are refreshed in batches of 10 to stay within rate limits.
  At 2000 req/hr from Yahoo, we can track ~600 unique tickers
  with 5-minute refresh cycles (600 * 12 cycles/hr = 7200 reads,
  but batching means ~60 API calls per cycle = 720/hr).


================================================================================
11. COMPETITION ENGINE
================================================================================

------------------------------------------------------------
11.1 COMPETITION LIFECYCLE
------------------------------------------------------------

  CREATE -> ACTIVE -> CALCULATING -> COMPLETED -> PAID_OUT

  Daily:
    Start: 00:00 UTC each day
    End: 23:59 UTC same day
    Roll: cron at 00:00 UTC closes previous, opens new

  Weekly:
    Start: Monday 00:00 UTC
    End: Sunday 23:59 UTC
    Roll: cron on Monday 00:00 UTC

  Monthly:
    Start: 1st of month 00:00 UTC
    End: Last day of month 23:59 UTC
    Roll: cron on 1st 00:00 UTC

------------------------------------------------------------
11.2 RANKING CALCULATION
------------------------------------------------------------

  Runs every 15 minutes via cron:

  1. For each active competition:
     a. Get all entries (competition_entries table)
     b. For each entry:
        - Fetch user's current portfolio total_equity
        - Calculate growth_pct = ((total_equity - starting_equity) / starting_equity) * 100
        - Update competition_entries.growth_pct
     c. Sort entries by growth_pct DESC
     d. Assign ranks (1, 2, 3, ...)
        Handle ties: same rank, next rank skips (1, 2, 2, 4)
     e. Write top 100 to leaderboard_cache table
     f. Invalidate KV leaderboard cache keys

  2. Performance optimization:
     - Only recalculate if any portfolio has changed since last calc
       (track via updated_at on portfolios table)
     - Use D1 batch operations for bulk updates
     - Process in chunks of 100 users at a time

  Prize assignment algorithm (runs when competition ends):
    1. Get final rankings

    4. Create payout records with status='pending'

    6. Queue batch notification for "competition ended" to all participants

11.4 MONTHLY RESET FLOW
------------------------------------------------------------

  Triggered: 1st of each month at 00:01 UTC

  For each active user:
    1. Close previous month's monthly competition
    2. Archive current portfolio (set is_active=0)
    3. Present reset choice screen in app (next app open):
       - Until user chooses, they cannot trade
       - Default to 'new' after 48 hours if no choice made

  When user chooses 'new':
    1. Create new portfolio with cash_balance=25000, total_equity=25000
    2. Set new portfolio as active
    3. Auto-enroll in current month's competitions

  When user chooses 'keep':
    1. Create new portfolio with:
       - Same positions as previous portfolio
       - Same cash balance
       - Same total equity
    2. Copy all positions to new portfolio
    3. growth_pct tracking starts from current equity (not 25K)
    4. Auto-enroll in current month's competitions

  Edge case: User who lost all money
    If total_equity < $100 when choosing 'keep', force 'new' portfolio.

    - All active users with is_active portfolio are auto-enrolled
    - Entry's starting_equity = portfolio's current total_equity
    - No manual enrollment needed
    - Users who joined mid-competition start from enrollment time

12. LEADERBOARD SYSTEM
================================================================================

------------------------------------------------------------
12.1 DATA FLOW
------------------------------------------------------------

  Every 15 minutes (cron):
    1. Calculate rankings for all active competitions
    2. Write top 100 per competition to leaderboard_cache table
    3. Write serialized leaderboard JSON to KV cache
    4. Each KV entry holds one page (50 entries) of one competition+tier combo

  On API request GET /leaderboard:
    1. Check KV: leaderboard:<comp_id>:<tier>:<page>
    2. If KV hit: return directly (fastest path, ~1ms)
    3. If KV miss: read from leaderboard_cache table in D1
    4. Compute user's own position:
       - Check KV: user:position:<user_id>:<type>
       - If miss: query competition_entries for user's rank
    5. Return combined response

------------------------------------------------------------
12.2 LEADERBOARD VIEWS
------------------------------------------------------------

  View: "Subscribed" (tier=premium)
    Shows only premium subscribers ranked against each other.
    Prizes shown next to qualifying ranks.

  View: "Free" (tier=free)
    Shows free users ranked against each other.
    Instead of prizes, shows "You could have won $X" message.
    Conversion upsell mechanism.

  View: "All" (tier=all)
    Combined ranking. Default view option.

------------------------------------------------------------
12.3 PERFORMANCE OPTIMIZATIONS
------------------------------------------------------------

  Problem: With 10K+ users, ranking calculation is expensive.

  Solution 1: Incremental ranking
    - Only re-rank users whose portfolios changed since last calculation
    - Use portfolios.updated_at > last_calculation_timestamp
    - Most users' portfolios change only when they trade (sparse updates)

  Solution 2: Materialized leaderboard
    - leaderboard_cache table serves as materialized view
    - Only top 100 are stored (not all users)
    - Rebuild from competition_entries when needed

  Solution 3: KV layering
    - KV serves ~99% of leaderboard reads
    - D1 only hit when KV expires or misses
    - KV TTL (5 min) << cron interval (15 min), so most reads are cached

  Solution 4: Partition by time period
    - Daily, weekly, monthly are independent calculations
    - Can run in parallel (separate queue messages)

15. PAYMENT SYSTEM

------------------------------------------------------------
15.1 SUBSCRIPTION (Apple IAP via StoreKit 2)
------------------------------------------------------------

  Product: com.jyanik.subscription.monthly ($6.99/month)

  Purchase flow:
    1. iOS app uses StoreKit 2 to present subscription
    2. User completes purchase in Apple's payment sheet
    3. iOS app receives Transaction from StoreKit 2
    4. iOS app sends transaction to backend:
       POST /payments/apple/verify
       { transaction_id: "...", product_id: "com.jyanik.subscription.monthly" }
    5. Backend verifies with App Store Server API:
       GET https://api.storekit.itunes.apple.com/inApps/v1/transactions/{transactionId}
       Authorization: Bearer <signed_jwt>
    6. On valid: update user subscription_tier='premium', subscription_expires_at
    7. Record in purchases table

  Server notifications (App Store Server Notifications V2):
    POST /payments/apple/webhook
    - Apple sends signed JWS notifications for:
      - SUBSCRIBED: new subscription
      - DID_RENEW: renewal success
      - EXPIRED: subscription expired
      - DID_FAIL_TO_RENEW: billing issue
      - REFUND: user got refund
      - REVOKE: family sharing revocation
    - Backend verifies JWS signature using Apple's public key
    - Updates user subscription status accordingly

  Subscription status check (on each API request):
    - JWT contains tier claim
    - If tier='premium' and subscription_expires_at < now:
      - Refresh subscription status from App Store Server API
      - If expired: update user to tier='free'
      - Issue new JWT with updated claims

15.2 VIRTUAL CASH PURCHASE (Apple IAP Consumable)
------------------------------------------------------------

  Product: com.jyanik.virtualcash.25k ($2.99)
  Type: Consumable (one-time purchase, can buy multiple times)

  Purchase flow:
    1. iOS app presents purchase via StoreKit 2
    2. On completion, verify with backend (same as subscription)
    3. Backend adds $25,000 to user's active portfolio cash_balance
    4. Record in purchases table with type='consumable'
    5. Finish transaction in StoreKit 2 (mark as consumed)

  Trigger: Portfolio total_equity drops below $10,000
    -> App shows "Out of Budget" screen with purchase option

15.3 PRIZE PAYOUTS
------------------------------------------------------------

  Flow:
    1. Competition ends -> prizes assigned -> payout records created (status: pending)
    2. Admin reviews pending payouts in admin dashboard
    3. Admin approves: PUT /admin/payouts/:id/approve
       -> Status changes to 'approved'
       -> Queue message: { type: "process_payout", payload: { payout_id } }
    4. Queue consumer processes payout:

       PayPal (primary):
         - Use PayPal Payouts API (https://api.paypal.com/v1/payments/payouts)
         - Send to user's registered paypal_email
         - Batch payouts to reduce API calls
         - On success: status='completed', processed_at=now
         - On failure: status='failed', failure_reason='...'

       Stripe (alternative):
         - Use Stripe Connect with Express accounts (future)
         - Or Stripe Transfers to user's connected account
         - More complex setup but better for compliance

    5. Notification sent to user on completion

  Minimum payout: $1.00
  Payout schedule: Weekly batch processing (Mondays)
  Holdback period: 7 days after competition end before payout eligible
    (fraud prevention, allows for challenge/review period)

16. RATE LIMITING
================================================================================

Implemented via KV counters with TTL-based windows.

------------------------------------------------------------
16.1 RATE LIMIT TIERS
------------------------------------------------------------

  Endpoint Group          Free Tier        Premium Tier     Window
  --------------          ---------        ------------     ------
  Auth endpoints          10 req           10 req           1 min
  Market data (quotes)    60 req           300 req          1 min
  Market search           20 req           100 req          1 min
  Screener runs           6 per day        unlimited        24 hr
  Trade execution         30 req           120 req          1 min
  Portfolio reads         60 req           300 req          1 min
  Leaderboard             30 req           120 req          1 min
  Chat messages           -                10 msg           1 min
  Chat reads              -                60 req           1 min
  Notifications           60 req           60 req           1 min
  Avatar upload           5 req            5 req            1 hr
  General (catch-all)     100 req          500 req          1 min

  Screener daily limit for free tier: tracked separately in D1
  (user_id + date compound key in a screener_usage table or via
   a counter in user_preferences).

------------------------------------------------------------
16.2 IMPLEMENTATION
------------------------------------------------------------

  KV key: rate:<user_id_or_ip>:<endpoint_group>
  Value: integer count
  TTL: window duration (60s for 1-minute windows)

  Middleware (runs before handler):
    async function rateLimit(request, env, ctx) {
      const key = `rate:${userId}:${endpointGroup}`
      const current = await env.CACHE.get(key, "text")
      const count = current ? parseInt(current) : 0

      if (count >= limit) {
        return Response.json(
          { ok: false, error: { code: "RATE_LIMITED", retry_after: ttl } },
          { status: 429, headers: { "Retry-After": ttl } }
        )
      }

      // Increment (fire-and-forget since KV is eventually consistent)
      ctx.waitUntil(env.CACHE.put(key, String(count + 1), { expirationTtl: ttl }))
      // Continue to handler
    }

  Note: KV-based rate limiting is approximate due to eventual consistency.
  For auth endpoints (where precision matters), use D1 or Durable Object
  for strict counting. For everything else, approximate is fine.

------------------------------------------------------------
16.3 GLOBAL RATE LIMITING
------------------------------------------------------------

  In addition to per-user limits, apply per-IP rate limiting
  at the Cloudflare level using Cloudflare WAF rate limiting rules:
    - 1000 requests per minute per IP (global)
    - Challenge (CAPTCHA) after 500 requests in 10 seconds (DDoS protection)

  {

    200 - Success
    201 - Created (new resource)
    204 - No Content (successful delete)
    400 - Bad Request (validation errors)
    401 - Unauthorized (missing/invalid token)
    403 - Forbidden (insufficient permissions or tier)
    404 - Not Found
    409 - Conflict (duplicate resource)
    422 - Unprocessable Entity (business logic rejection)
    429 - Too Many Requests (rate limited)
    500 - Internal Server Error

  Rollback: manual (write reverse migration and apply)
  D1 does not support ALTER TABLE ... DROP COLUMN, so migrations
  must be additive. Use new columns + application-level migration.

  Scaling costs:
    Workers: $0.50 per million requests beyond 10M

    KV: $0.50 per million reads beyond 10M
    R2: $0.015 per GB stored beyond 10GB
    DO: $0.15 per million requests

  At 10K users with moderate activity, estimated monthly cost: ~$15-30
  At 100K users: ~$100-300/month

------------------------------------------------------------
20.6 WORKER SIZE LIMITS
------------------------------------------------------------

  Free plan: 1MB per worker (after gzip)
  Paid plan: 10MB per worker (after gzip)

  api-main worker is the largest. To stay within limits:
    - Use tree-shaking and minification (esbuild, default with Wrangler)
    - Lazy-load heavy modules (e.g., bcrypt WASM only in auth worker)
    - Keep route handlers lean, delegate to shared utility functions
    - External heavy processing to queues

  If api-main grows too large, split into:
    - api-portfolio (portfolio + trade routes)
    - api-social (leaderboard + notifications)
    - api-market (market data routes)
    - api-admin (admin routes)
  But start with a single worker for simplicity.
