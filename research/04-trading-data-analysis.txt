## 1. TRADING ENGINE ARCHITECTURE

### 1.1 High-Level Overview

The trading engine is located under `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/` and implements a **paper-trading / simulated-trading system**. It is not connected to a real brokerage. Users start with a virtual cash balance of $25,000 and can execute simulated buy and sell operations against real-time stock price data fetched from the IEX Cloud API.

The engine is organized into four subsystems: **Balance Management**, **Transaction Logging**, **Transaction Ledger**, and **Stock Split Handling**.

### 1.2 Core Orchestrator: `TradingEngine`

**File:** `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/TradingEngine.swift`

`TradingEngine` is a singleton (`TradingEngine.shared`) that serves as the central coordinator. It holds references to:

- `BalanceManager` -- manages cash and equity totals
- `TransactionLoggingManager` -- writes transaction logs (local CoreData + remote Firestore)
- `LedgerManager` -- maintains the canonical ledger of active positions

**Buy Flow:**
1. `buy(transaction:completion:)` is called.
2. `validatePurchaseAttempt` checks whether `tradePrice * numberOfShares <= currentCashBalance`.
3. If valid, `TransactionLoggingManager.log()` fires, which first writes to Firestore (remote), then to the local CoreData `LoggedTransaction` entity.
4. `LedgerManager.save()` persists the transaction as a `PersistedTransaction` in CoreData.
5. `BalanceManager.handleBuy()` debits the cash balance.
6. An analytics event is reported.

**Sell Flow:**
1. `sell(transaction:completion:)` is called.
2. There is NO validation gate in the sell method itself (unlike buy). Validation exists as a separate method `validateSaleAttempt` but it must be called externally before invoking `sell`.
3. The same logging and ledger persistence occurs.
4. `BalanceManager.handleSell()` credits the cash balance.

**Holdings Loading Flow:**
1. `loadHoldings()` calls `mapTransactionsToHoldings` which fetches all `PersistedTransaction` records from CoreData.
2. `HoldingMapper` groups transactions by ticker, creates `Holding` objects, and fetches current prices from the network (`StockPriceLoader`).
3. Equity balance is updated.
4. Stock split checks execute (once per day).
5. Results are propagated through `CompletionHandler<[Holding]>` (a custom observer/notification pattern).
6. `ProfileSyncCoordinator.sync()` pushes holdings + performance data to Firestore.

### 1.3 Balance Management

**File:** `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Balance Manager/BalanceManager.swift`

`BalanceManager` stores two values using `UserDefaults`:
- `cash` -- initialized to $25,000 (`BalanceConstants.initialCash`)
- `equity` -- total portfolio value (cash + stock holdings value)

Key observations:
- Balances are persisted in **UserDefaults only**, not CoreData. This means they are not recoverable from transaction history alone if UserDefaults is cleared. There is no reconciliation mechanism.
- `currentCashBalance` and `totalEquityBalance` are `lazy var` properties that read from UserDefaults on first access and are then cached in memory. Subsequent mutations modify the in-memory value AND save to UserDefaults.
- `handleEquityUpdate(with:)` recalculates total equity as `stockHoldingValue + currentCashBalance`.

### 1.4 Ledger Subsystem

**Files:**
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Ledger/LedgerManager.swift`
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Ledger/LocalTransactionLedgerLoader.swift`

### 1.5 Logging Subsystem

**Files:**
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Logging/TransactionLoggingManager.swift`
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Logging/Local/LocalTransactionLogger.swift`
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Logging/Local/TransactionLogLoader.swift`
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Logging/Protocols/TransactionLogger.swift`
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Logging/Remote/RemoteTransactionLogger.swift`

The logging system follows the **Strategy pattern** via the `TransactionLogger` protocol. Two implementations exist:

1. **`LocalTransactionLogger`** -- persists to the `LoggedTransaction` CoreData entity.
2. **`RemoteTransactionLogger`** -- writes to Firestore under the `"transactions"` collection, keyed by random UUID. Includes the user's profile ID.

`TransactionLoggingManager` orchestrates: remote fires first, then local on completion. The log is separate from the ledger -- the log is an audit trail (sorted by date descending), while the ledger is the active position set.

### 1.6 Stock Split Handling

**Files:**
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Stock Split/StockSplit.swift`
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/Stock Split/StockSplitFetcher.swift`
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Features/StockSplitHandler.swift`

`StockSplit` is a `Decodable` struct with `toFactor`, `fromFactor`, and `exDate`. The ratio is `toFactor / fromFactor`.

`StockSplitFetcher` hits IEX Cloud's `/splits/1yr` endpoint for each ticker.

`StockSplitHandler` applies splits to existing transactions by:
1. Checking if the split's ex-date is after the most recent transaction date AND after the last applied split date.
2. Adjusting `tradePrice = tradePrice / ratio` and `numberOfShares = numberOfShares * ratio`.
3. Setting `lastAppliedStockSplit` to the ex-date.

The check runs once per calendar day (`shouldCheckForStockSplit` uses a UserDefaults-stored date). Multiple handlers execute in a `DispatchGroup` for all held tickers.

### 1.7 Transaction Protocol and Models

**Protocol:** `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Protocols/Transaction.swift`

```swift
protocol Transaction: class {
    var ticker: String { get set }
    var numberOfShares: Int32 { get set }
    var tradePrice: Double { get set }
    var type: String { get set }
    var transactionDate: String { get set }
    var id: String { get set }
    var lastAppliedStockSplit: Date? { get set }
}
```

Three concrete conforming types:
1. **`PersistedTransaction`** (NSManagedObject) -- ledger entity
2. **`LoggedTransaction`** (NSManagedObject) -- log entity
3. **`TransactionAdapter`** (plain class) -- in-memory adapter for creating transactions outside CoreData context

`TransactionType` is a simple enum: `.buy` or `.sell`, with string raw values.

### 1.8 Holdings Model

**Files:**
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Models/Holdings/Holding.swift`
- `/Users/elshanmagsudov/upful-ios/Upful/Custom APIs/Trading Engine/Models/Holdings/HoldingMapper.swift`

`Holding` is a plain class (not CoreData) that aggregates transactions for a single ticker. It computes:
- `totalShareCount` = sum of buy shares minus sum of sell shares
- `currentTotalValue` = currentPrice * totalShareCount
- `averagePrice` = weighted average of buy prices
- `totalPriceMovementDollar` and `totalPriceMovementPercent` -- P/L calculations

`HoldingMapper` performs the aggregation: it takes all ledger transactions, groups by ticker using an imperative loop, filters out positions with zero shares, and fetches live quotes via `StockPriceLoader` in a `DispatchGroup`.

## 8. DATABASE SCHEMA ISSUES AND LIMITATIONS

### 8.1 Critical Issues

1. **Orphaned xcdatamodel**: `TransactionLog.xcdatamodeld` has `representedClassName="PersistedTransaction"` for the `LoggedTransaction` entity, which is incorrect. This model appears outdated and may conflict if loaded.

2. **Missing relationship in StockDataModel**: The code for `SavedScreener` declares a `savedScreenerParameter: NSSet` relationship to `SavedScreenerParameter`, but neither entity nor relationship exists in `StockDataModel.xcdatamodel`. The `SavedScreenerParameter` entity and its inverse relationship are defined only in Swift code, with no backing schema.

3. **Balance not backed by transactions**: The cash balance in UserDefaults can drift out of sync with actual transaction history. If UserDefaults is cleared or corrupted, the balance cannot be reconstructed.

4. **No uniqueness constraints on transactions**: Both `PersistedTransaction` and `LoggedTransaction` lack uniqueness constraints. A crash during the buy/sell flow could result in duplicate entries.

5. **transactionDate stored as String**: Dates are stored as strings in varying formats. The `DateTransformer` uses force-unwraps that will crash on unexpected formats. String-based date storage also prevents efficient date-range queries using CoreData predicates (the `loadTransactions(startingFrom:)` method performs a string comparison on the formatted date, which only works correctly because the format is year-first).

6. **12-hour time format bug**: `Date.asString` uses `hh` (12-hour) instead of `HH` (24-hour) and does not include AM/PM. Transactions at 1 PM and 1 AM will produce identical date strings.

### 8.2 Moderate Issues

7. **Two separate NSPersistentContainers**: `PersistenceService` and `TransactionContainerManager` manage separate SQLite databases. The `User` entity lives in `TransactionDataModel` while user-related screeners and saved stocks live in `StockDataModel`. There is no cross-store reference mechanism.

8. **No migration strategy**: Both data models lack versioning beyond the initial version. Any schema changes would require manual migration handling.

9. **Force-unwraps in date parsing**: `DateTransformer.convertStringToDate` and `ProfileDataManager.convertToDate(from:)` force-unwrap, creating crash vectors for any malformed date string.

10. **`LedgerManager.delete()` is a no-op**: The method body is empty, meaning transaction deletion is not functional.

11. **`TransactionLedgerPersistence.delete()` deletes ALL records**: The delete method fetches ALL `PersistedTransaction` records (no predicate filter) and deletes them all, rather than deleting the specific transaction passed as parameter.

## 10. SUMMARY OF KEY ARCHITECTURAL PATTERNS

| Pattern | Where Used |
|---------|-----------|
| **Singleton** | `TradingEngine.shared`, `TransactionContainerManager.shared`, `PersistenceService.shared`, `ProfileSyncCoordinator.shared`, `UserProfile.instance` |
| **Protocol-Oriented Abstraction** | `Transaction`, `TransactionLoader`, `TransactionLogger`, `CoreDataModelContainerManager`, `StockViewable`, `MenubarContainerProtocol` |
| **Strategy Pattern** | `TransactionLogger` with `LocalTransactionLogger` and `RemoteTransactionLogger` |
| **Adapter Pattern** | `TransactionAdapter` bridges plain objects to the `Transaction` protocol |
| **Observer Pattern** | `CompletionHandler<T>` with subscribe/unsubscribe/notify |
| **Facade Pattern** | `TradingEngine` facades balance, logging, and ledger subsystems |
| **Parent-Child CoreData Contexts** | `TransactionContainerManager` background context with viewContext parent |
| **Dispatch Groups** | Holdings loading (price fetching) and stock split checking |
| **Programmatic UI** | All UI construction via code with auto-layout helper extensions |
